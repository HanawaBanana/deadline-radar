Deadline Radar — app map

A take-home map of the code: one real action, the pieces it touches, and the places to start when you want to change something. Generated from the working tree at commit b4c38f9 plus the planning documents in devpost/. It is a snapshot and can drift.

What the app is

One local page. You paste the text of an announcement; a reader proposes values with quotes; deterministic Python decides which of them are true and shows its work; the result is a brief, two exports (a calendar and a self-contained HTML file) and a local history. Three pieces, deliberately different kinds of thing: reader (may hallucinate) → validator (cannot) → brief (shows both).

One action, end to end

A 3-stop route (reference)

Reference route prepared from the finished code; it was not toured interactively, so treat it as directions rather than a completed walkthrough.

  1. The paste and the request — templates/index.html (the form and the download row) → static/app.js (posts {"text": …, "mode": …} to /api/analyse and swaps in the returned fragment). What to look for: the brief is not built in the browser — the server returns finished markup, so a screenshot and a user see the same thing.
  2. Where “true” is decided — radar/web.py (Handler.do_POST → radar/pipeline.py) → radar/validate.py :: analyse() (line ~372), which calls validate_date_field(), validate_prize_field() and validate_text_field(); dates go to radar/dates.py, money to radar/money.py. What to look for: the quote is looked up in the pasted text (Page), and a number that is not on the page produces verdict rejected with a reason — never a silent fix.
  3. What comes out — radar/render.py (field_rows(), rejected_table(), source_html()), then the two exports: radar/ics.py :: build() and radar/export.py :: brief_html(), offered by the routes in radar/web.py and stored by radar/store.py :: Store.save(). What to look for: the calendar writes only dates that survived the validator, and the exported HTML has no external reference at all.

To change this, start here

You want to change…Start at
what the offline reader looks for (a new field, another date format) radar/offline.py :: extract(), then teach radar/validate.py how to judge the new field
a verdict rule (when something is rejected or corrected) radar/validate.py — the per-kind functions; the rules are listed in devpost/spec.md > Validation rules
how a date or a prize is rendered radar/dates.py, radar/money.py
the look of the brief static/style.css for the app, radar/export.py for the exported file (it carries its own inline styles)
what the model reader is asked for radar/extract.py (the prompt and the one HTTP call)
how the demo video is produced radar/demo.py (one state per URL) and tools/make_video.py
The tiny edit that was kept

During this build pass the download row gained a second link (Download brief (.html)) in radar/render.py :: result_html(), pointing at /api/analysis/<id>.html. Visible effect: after an analysis, the head of the brief offers both files. The check that it worked: tests/test_api.py asserts the link and the attachment headers, and tests/test_export.py asserts the exported document has no external reference.

A practice to reuse

Write the rule as a visible rejection, then put a test on it. In this project the rule “a value containing a number that is not on the page is rejected” lives in devpost/spec.md > Validation rules (rule 3), is implemented in radar/validate.py, and is pinned by tests/test_validate.py and tests/test_money.py; the demo tour step /?demo=6 shows the same rule to a human with the fabricated amount beside the rejection.

The reusable part is the shape, not the topic: decide the rule → make it observable in the interface → keep one check that fails the moment the rule regresses. It works the same way for a pricing rule, a permission rule or a validation rule in the next project.
